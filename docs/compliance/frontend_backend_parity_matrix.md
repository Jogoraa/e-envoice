# Directive No. 1142/2026 — Frontend / Backend Parity Matrix
**UT Electronic Invoicing System (UT Invoice)**  
**Document Version:** 1.0.0  
**Date:** 2026-10-05  
**Compliance Standard:** FDRE Ministry of Revenues Directive No. 1142/2026 & Annexes 1–2

This document provides complete, line-by-line parity tracking between backend statutory capabilities and Flutter application surfaces across the three product boundaries:
1. **Tenant / Client Application** (Taxpayer Operational Portal & mPOS)
2. **SaaS Management Application** (UT Invoice Operational & Onboarding Staff)
3. **Master Admin Application** (Platform Governance, Security & Tax Authority Portal)

---

## Status Classification Legend
- **NOT_STARTED:** No Flutter UI or API binding exists.
- **PARTIAL:** Screen or form exists but lacks complete fields, states, or statutory workflow steps.
- **UI_ONLY:** Screen/mock UI exists without real backend API binding.
- **API_CONNECTED:** Real backend API connected with Dio/Riverpod; requires E2E verification or test coverage.
- **E2E_VERIFIED:** Full user action -> Flutter UI -> Validation -> API -> DB/Outbox -> Response -> Visible outcome verified with tests.
- **NOT_APPLICABLE:** Statutory requirement applies exclusively to backend/infrastructure with zero UI interaction.
- **EXTERNAL_DEPENDENCY:** Blocked by external third party (e.g. INSA hardware HSM, physical telecom SMSC).
- **BLOCKED:** Blocked by dependent upstream feature.
