# Threat Model & Security Architecture
## UT Electronic Invoicing Platform (Directive No. 1142/2026 Compliant)
### Methodology: STRIDE & Financial Integrity Threat Analysis

---

## 1. Executive Summary & Security Objectives

As regulated national financial infrastructure operating under the supervision of the Ethiopian Ministry of Revenues (MoR) and the Information Network Security Administration (INSA), the UT Electronic Invoicing Platform enforces rigorous defense-in-depth controls.

### Core Security Objectives:
1. **Absolute Tenant Isolation**: No tenant can ever view, modify, or infer another tenant's financial, tax, or operational data.
2. **Financial Immutability**: Registered tax invoices cannot be updated or erased under any circumstance.
3. **Cryptographic Integrity & Signature Verification**: Invoices, signatures, and audit trails must be verifiable against INSA-approved digital certificates.
4. **Resilience Against Fraud & Manipulation**: Counter evasion, sequence manipulation, out-of-geofence sales, and offline replay attacks are structurally blocked.

---

## 2. STRIDE Threat Analysis & Mitigations

### 2.1 Spoofing (Identity & Device Impersonation)
- **Threat T1: Client Impersonation**: Attacker attempts to forge an ERP or POS client to register unauthorized invoices under another business's TIN.
  - *Mitigation*: Multi-layered authentication requiring an API Key + HMAC Request Signature + OAuth2 JWT. The server resolves the `tenant_id` exclusively from trusted cryptographic claims, never from client-supplied HTTP headers (`X-Tenant-ID` is ignored if unverified).
- **Threat T2: Rogue POS Device Registration**: An unauthorized device attempts to submit transactions using a stolen branch credential.
  - *Mitigation*: Device-level binding with X.509 device certificates, strict device status checks (`ACTIVE`), and periodic GPS verification against registered branch geofences (Directive Art. 4(5)).

### 2.2 Tampering (Data Modification & Integrity Attacks)
- **Threat T3: Post-Registration Financial Alteration**: A malicious insider attempts an SQL `UPDATE` to decrease reported VAT or total sales amounts on registered invoices.
  - *Mitigation*: Application-level immutability (JPA entity `@ReadOnly` or absence of setter methods), database triggers preventing updates to rows where `registration_status = 'REGISTERED'`, and append-only financial ledger design. Corrections are only permitted through distinct Credit/Debit Notes (Art. 25) or approved Cancellations (Art. 26).
- **Threat T4: Audit Trail Tampering**: An administrator deletes or alters audit logs to hide fraudulent adjustments.
  - *Mitigation*: Hash-chained audit log structure (`SHA-256(previous_event_hash + current_event_payload)`). Any alteration of historical logs breaks the chain validation. In production, logs are replicated to append-only WORM (Write Once, Read Many) cloud storage.
- **Threat T5: QR Code Counterfeiting**: A seller generates fake QR codes on printed receipts that don't match the MoR registration.
  - *Mitigation*: The QR payload contains the cryptographic digital signature issued by the Ministry of Revenues EIRS (`signedQR`). The public Authority verification portal validates the digital signature against the MoR public key.

### 2.3 Repudiation (Disavowal of Transactions)
- **Threat T6: Disavowal of Invoices**: Taxpayer claims an invoice was generated by a system error or unauthorized party to avoid tax liability.
  - *Mitigation*: Every transaction payload is digitally signed with the tenant's INSA-certified private key using Bouncy Castle before transmission. The transaction captures actor ID, client IP, device ID, exact timestamp, and document sequence counter.
- **Threat T7: Disavowal of Offline Transactions**: Taxpayer claims offline sales receipts were fabricated by the device.
  - *Mitigation*: Pre-allocated offline number sequences tied to specific device hardware IDs, with cryptographic sequence signatures created at transaction time.

### 2.4 Information Disclosure (Data Leakage)
- **Threat T8: Cross-Tenant Data Access (IDOR)**: An attacker manipulates an invoice ID in a REST request (`GET /api/v1/invoices/{uuid}`) to inspect a competitor's invoice.
  - *Mitigation*: Every JPA query and repository method enforces a mandatory `WHERE tenant_id = :currentTenantId` filter injected from the authenticated `TenantContext`. Hibernate filters and PostgreSQL row-level security (RLS) provide defense-in-depth.
- **Threat T9: Exposure of MoR API Keys & INSA Private Keys**: Private keys leaked through application logs, error messages, or Git repositories.
  - *Mitigation*: Zero secret storage in relational database columns or Git. All cryptographic private keys and MoR Client Secrets are hosted in HashiCorp Vault / Cloud KMS. Automated log masking filters out authorization headers, tokens, and private key representations.

### 2.5 Denial of Service (Availability Attacks)
- **Threat T10: Offline Replay Flooding**: A compromised or misconfigured POS dumps millions of historical offline transactions, exhausting server resources.
  - *Mitigation*: Token bucket rate-limiting in Redis per device and tenant, batch size limits (max 100 transactions per sync request), and strict sequence continuity validation.
- **Threat T11: Government Gateway Outage Cascading Failure**: MoR EIRS endpoint experiences an outage, causing thread exhaustion in the invoicing platform.
  - *Mitigation*: Resilience4j circuit breaker with fallback to the `OFFLINE_BUFFERED` queue, asynchronous non-blocking WebClient I/O, and Virtual Threads to prevent connection thread pools from starving.

### 2.6 Elevation of Privilege
- **Threat T12: Cashier to Tenant Admin Escalation**: A cashier user attempts to modify tax rates, adjust numbering sequences, or view audit logs.
  - *Mitigation*: Spring Security 6 fine-grained method security (`@PreAuthorize("hasAuthority('invoice:admin')")`) combined with scope enforcement on all endpoints.
- **Threat T13: Tenant User Accessing Authority Auditor Endpoints**: A business user attempts to query the national audit inspection API.
  - *Mitigation*: Authority endpoints (`/api/v1/authority/**`) require dedicated mTLS client certificates and the distinct `ROLE_AUTHORITY_AUDITOR` role, isolating tax inspection from standard tenant traffic.
